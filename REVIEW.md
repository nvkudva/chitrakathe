# Code review — chitrakathe

A paid Indian-language video-trailer service: a Next.js web tier writes an event row and a pg-boss message, and a separate Node worker renders a template storyboard into MP4s with ffmpeg and headless Chromium, under a hard per-job cost ceiling, unlocked by a Razorpay payment.

Read in full: `package.json`, `CLAUDE.md`, `.env.example`, `docs/known-gaps.md`, `.github/workflows/ci.yml`, all `db/migrations/*.sql`, `scripts/migrate.ts`, `scripts/retention.ts`, every file under `src/lib/` except `i18n/ui.ts` and `theme.ts`, every route under `src/app/api/`, `worker/index.ts`, and the test files. Skimmed only: `src/components/BriefForm.tsx` (submit path only), `src/lib/render/cards.ts` (browser + HTML generation), `src/lib/render/motion.ts`, `src/lib/cost/report.ts` (first half), the marketing/legal pages, `prd.md`, and `README.md`.

## Architecture

Three processes over one Postgres. The web tier (`src/app/api/**`) validates with zod, authorises, writes rows, and enqueues; the worker (`worker/index.ts`) drains `QUEUES.render` and calls `renderBrief`; `scripts/retention.ts` runs as a cron. pg-boss shares the database (`src/lib/queue.ts:21`), so job state and domain state are transactional together and there is no Redis. `src/lib/db.ts` memoises one `postgres` pool; `src/lib/config.ts` memoises one zod-parsed env object. State lives in exactly two places: Postgres rows and an object store behind `src/lib/storage` (`storage()` / `keys.*`).

The layering is genuinely enforced, not just documented. `renderBrief` (`src/lib/render/pipeline.ts:56`) takes a `Brief`, a `CostLedger`, and a `loadPhoto` callback, and returns file paths — it never touches the database, the queue, or the storage driver. That is what makes `scripts/render-brief.ts` and `scripts/check-cost-once.ts` able to exercise the whole pipeline offline from `fixtures/brief.namakarana.json`. Providers are behind three small interfaces (`VideoProvider`, `TtsProvider`, `ModerationProvider`) selected by config, with a stub for each. `src/lib/repo.ts` is the only module writing SQL for the domain tables, apart from three deliberate exceptions in route handlers.

Two structural decisions carry the business. First, spend is funnelled through `CostLedger` (`src/lib/cost/ledger.ts`), which quotes before it charges and refuses rather than overruns; `videoPrice()` throws on an unpriced model so the ceiling can never be enforced against an unknown number. Second, the free-render decision and the job insert happen inside one transaction holding `select ... for update` on the event row (`src/app/api/events/[id]/render/route.ts:79-112`), which is the correct fix for the race the comment describes.

Where it will hurt:

- The web tier reaches around `repo.ts` in three places — `src/app/api/events/route.ts:44`, `src/app/api/events/[id]/render/route.ts:47` and `:79-112`, `src/app/api/jobs/[id]/route.ts:21`, `src/app/api/download/[jobId]/route.ts:28`. The ownership check `select 1 from events where id = ? and user_id = ?` is written out four times. There is no `events` service module, so the second person to add an authorised route will write a fifth copy, and there is no single place to change when ownership stops being one column.
- Cost accounting has a hole in the layering: moderation is paid for in the web tier (`src/app/api/events/[id]/assets/route.ts:58`) before any job exists, so `CostLedger.chargeModeration` (`ledger.ts:141`) has no callers and the ceiling covers only render-time spend. The invariant in `CLAUDE.md` ("`CostLedger` is the only thing allowed to spend money") is already false.
- `renderBrief` is one 100-line function doing photo normalisation, TTS, the per-aspect shot loop, assembly, watermarking, and cost settlement, with progress percentages hardcoded as arithmetic on loop indices (`pipeline.ts:107`, `:118`, `:124`). Adding a sixth stage means recomputing four magic constants.
- `src/lib/render/cards.ts` holds one module-global `browser`, and `renderBrief`'s `finally` calls `closeBrowser()` (`pipeline.ts:153`). That is correct only because the worker runs `batchSize: 1`. The moment a second concurrent render lands in the same process, one job's teardown kills the other's browser mid-capture.

## Code quality

TypeScript is used well: `strict` plus `noUncheckedIndexedAccess` in `tsconfig.json`, no `any` or `as any` anywhere in `src`, `worker`, or `scripts`. Discriminated unions on `Shot` make `renderShot` (`pipeline.ts:217`) exhaustive without a default case. Money is integer paise throughout, with the rule stated once in `src/lib/money.ts:3` and honoured everywhere including the schema (`db/migrations/0001_init.sql`). Error handling at the HTTP boundary is deliberate — `readJson` and `guard` (`src/lib/http.ts`) turn malformed bodies and unexpected throws into clean 400s and detail-free 500s, and every `api/` route except the two auth routes is wrapped.

The comments are the best thing here. Nearly every non-obvious line explains the incident that produced it — `repo.ts:74` on non-UUIDs reaching a uuid column, `eventAccess.ts:46` on `timingSafeEqual` throwing on byte-length mismatch, `pipeline.ts:204-212` on the `genCache`, `queue.ts:36` on the singleton key. `docs/known-gaps.md` is an unusually honest inventory of what is not done and what closing it costs.

Problems:

- **`src/lib/storage/` is not in the repository.** `.gitignore:9` contains `storage/` with no leading slash, so git ignores `src/lib/storage/` as well as the intended `./storage` data directory. `git ls-files` returns nothing matching `storage`, and eight modules import it — `worker/index.ts:8`, `scripts/retention.ts:10`, `src/app/t/[jobId]/page.tsx:5`, `src/app/api/{download,jobs,files}/...`, `src/app/api/events/[id]/{uploads,assets}/route.ts`. A fresh clone cannot typecheck, build, or run, which means the CI job in `.github/workflows/ci.yml` cannot be passing.
- **A retried job gets a fresh ceiling.** `worker/index.ts:33` constructs `new CostLedger(jobId, repo.recordCost, job.ceiling_paise)` with an empty entry list and never loads the `cost_entries` already recorded for that job. `enqueueRender` sets `retryLimit: 2` (`queue.ts:32`) and `handleRender` rethrows non-ceiling errors to trigger the retry (`worker/index.ts:97`), so a job that fails twice after spending model money can spend up to three ceilings in total. `render_jobs.cost_paise` accumulates correctly in the database; nothing reads it back.
- **Finished renders are copied to local disk and never deleted.** `publish()` (`pipeline.ts:159-161`) copies master, preview, and poster into `config().STORAGE_LOCAL_DIR/renders/<jobId>` regardless of `STORAGE_DRIVER`. With `STORAGE_DRIVER=s3` the worker uploads a second copy to S3, and `scripts/retention.ts` only calls `store.delete`, which touches the S3 objects. The local copies accumulate forever on the render box.
- **`settlePayment` marks every job for the event paid.** `src/lib/payments.ts:53`: when a payment carries no `job_id`, `update render_jobs set paid = true where event_id = ?` sets the flag on all of them. `costSummary` counts `count(*) filter (where paid)` (`src/lib/cost/report.ts:47`), so an event with two re-renders and one ₹499 unlock reports three paid jobs — the conversion rate and both margin figures on `/admin/costs` are wrong in the optimistic direction.
- **The dev signing secret is only refused in production.** `src/lib/auth/session.ts:30` throws when `SIGNING_SECRET` is the default *and* `NODE_ENV === "production"`. `config.ts:19` defaults `NODE_ENV` to `"development"`, and `CLAUDE.md` instructs operators never to pin it in `.env`. A staging or self-hosted deployment that does not set it runs with the publicly known key from `.env.example`, which signs both session cookies and storage URLs.
- **A hardcoded font path can fail every preview after all the money is spent.** `pipeline.ts:471` uses `/usr/share/fonts/truetype/dejavu/DejaVuSans-Bold.ttf` with no config entry and no existence check. CI installs `fonts-noto-core`, not `fonts-dejavu-core`, so this path is not exercised anywhere in CI, and the watermark step runs after the generative shots have already been paid for.
- **Test coverage is unit-only.** Five files, all pure functions: cost ledger arithmetic (`tests/cost.test.ts`), session HMAC (`tests/auth.test.ts`), UUID and token shape (`tests/access.test.ts`), template schema (`tests/templates.test.ts`), text slots (`tests/text.test.ts`). They are well-written and test the right invariants. Nothing covers a route handler, the render-decision transaction, `settlePayment` idempotency, webhook signature verification, or the worker's retry path — i.e. every place money moves.
- **PII in logs.** `src/lib/delivery.ts:47` and `:52` log the family's email address or phone number together with the trailer link at info level, on every render, twice per render. `maskPhone` exists in the same file and is not used.
- Dead exports: `verifyCheckoutSignature` (`razorpay.ts:42`), `chargeModeration` (`ledger.ts:141`), `maskPhone` and `whatsappShareUrl` (`delivery.ts:38,56`), `isPlaceholder` (`legal.ts`, which `docs/known-gaps.md` says a launch check should call), `STAGES` (`pipeline.ts:498`).
- Config and secrets are handled well otherwise: one zod schema, no secret in the repo, `.env` ignored, every provider throwing a named error when its key is missing.
- Dependency hygiene is good — ten runtime dependencies, no payment SDK, no auth framework, `package-lock.json` committed, `npm ci` in CI. There is no `packageManager` field and no lint step in the pipeline.

## Risks

- **Unauthenticated event creation with no rate limit.** `POST /api/events` (`src/app/api/events/route.ts:130`) requires no session and no captcha, and inserts a `users` row with a caller-supplied email or phone (`repo.ts:36`). There is no rate limiting anywhere in the codebase. That is unbounded row growth and unbounded email-address seeding.
- **Repeat moderation is billable and unmetered.** `POST /api/events/[id]/assets` re-runs `mod.checkImage` for every key on every call (`assets/route.ts:47-63`), with no dedupe against `moderation_results` and no ceiling. A caller holding one event token can loop it and bill Sightengine indefinitely.
- **Unverified-email account merge.** `upsertGoogleUser` matches on `google_sub` **or** `email` (`session.ts:109`). A user row created anonymously via `POST /api/events` with someone else's email address is adopted, with its events, by that person's first Google sign-in.
- **No session revocation.** The session cookie is a 30-day self-contained HMAC (`session.ts:15`, `:81`) with no server-side check that the user still exists. Sign-out clears the cookie only; the only way to invalidate a stolen one is to rotate `SIGNING_SECRET`, which simultaneously invalidates every outstanding signed storage URL.
- **Admin token travels in the query string.** `/admin/costs?token=...` (`src/app/admin/costs/page.tsx:14-17`), compared with `!==` rather than a constant-time compare. Query strings land in access logs, proxy logs, browser history, and outbound `Referer` headers.
- **Chromium runs with `--no-sandbox`** (`cards.ts:36`) on the worker box, which also holds the S3 credentials and the database URL. Family text is escaped (`cards.ts:151`), but template-supplied font names and palette colours are interpolated into a `<style>` block unescaped (`cards.ts:163-196`) — safe only while templates are repo-controlled JSON.
- **Migrations have no checksum.** `scripts/migrate.ts:13` keys on filename alone, so editing an already-applied migration is silently a no-op in every environment that has run it. `0001_init.sql:59` also uses a bare `create type`, so a partially-applied migration cannot be re-run.
- **Storage keys are guarded in one route, not centrally.** The `uploads/<id>/` prefix and `..` check live inline at `assets/route.ts:37-41`. `resolveKey` in `api/files/[key]/route.ts:14` does the equivalent for the local driver. Both are correct; neither is shared, so the next route that accepts a key will need to remember.
